## Індекс має відповідати запиту

Індекс прискорює певні способи пошуку, але додає місце на диску й роботу під час INSERT, UPDATE та DELETE. Починай з реального запиту: які поля мають рівність, де є діапазон, у якому порядку потрібен результат і скільки рядків повертається.

```sql
CREATE INDEX orders_customer_paid_id_idx
ON orders (customer_id, id)
WHERE status = 'paid';

SELECT id, customer_id, total_cents
FROM orders
WHERE customer_id = $1 AND status = 'paid' AND id > $2
ORDER BY id ASC
LIMIT $3;
```

Індекс спочатку групує записи за клієнтом, потім за id. Часткова умова зберігає тільки оплачені записи, бо саме їх читає цей endpoint. Користь залежить від розподілу даних; якщо майже всі записи оплачені, виграш частковості може бути невеликим.

## EXPLAIN — пояснення вибору планувальника

`EXPLAIN` показує заплановані операції та оцінки. `EXPLAIN (ANALYZE, BUFFERS)` реально виконує запит і додає виміряні рядки, час та роботу з буферами. Для запитів, які змінюють дані, враховуй цей побічний ефект: аналіз треба виконувати на безпечному стенді.

Порівнюй оцінену та фактичну кількість рядків. Велика різниця може вказувати на застарілу статистику або складний розподіл даних. Seq Scan сам по собі не є доказом проблеми: прочитати маленьку таблицю цілком іноді дешевше, ніж переходити від індексу до рядків.

Keyset-пагінація використовує `id > afterId`. Вона не змушує щоразу відкидати великий OFFSET, але потребує стабільного порядку. Якщо порядок зміниться на `created_at, id`, зміняться cursor і придатний індекс.

Автотест перевіряє наявність потрібного індексу та правильні сторінки, але не вимагає конкретного фізичного плану для кількох рядків. Далі створи характерний обсяг у PostgreSQL, онови статистику через `ANALYZE`, виміряй читання й вставки та обґрунтуй індекс фактами. Один «швидкий» запуск на порожній таблиці для цього недостатній.
