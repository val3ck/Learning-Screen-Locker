## Repository задає вузьку межу даних

Repository приховує техніку зберігання за зрозумілими операціями: знайти користувача, прочитати список, зберегти замовлення. Це не вимога створювати абстракцію для кожної таблиці. Користь з’являється там, де бізнес-коду потрібен стабільний контракт, а деталі SQL і драйвера не мають розповзатися по всіх маршрутах.

```js
export async function findByEmail(db, email) {
  const result = await db.query(
    'SELECT id, email FROM users WHERE email = $1',
    [email]
  );
  return result.rows[0] ?? null;
}
```

Текст SQL і значення передаються окремо. Email із лапкою залишається даними, а не перетворюється на частину структури запиту. Параметри призначені для значень: назву таблиці чи напрям сортування через `$1` не підставиш. Динамічні ідентифікатори потребують контрольованого переліку та коректного формування SQL.

## Pool є ресурсом процесу

Pool повторно використовує обмежений набір з’єднань. Зазвичай його створюють на рівні застосунку, а не для кожного HTTP-запиту. Кількість інстансів сервера множиться на розмір pool, тому допустимий ліміт треба узгодити з можливостями бази. Для транзакції отримують окремий client і звільняють його у `finally`.

Повернення `null` для відсутнього одиничного запису — частина repository-контракту. HTTP-шар пізніше вирішить, чи означає це `404`, а бізнес-операція — чи можна створити новий запис. Драйверні помилки теж не повинні випадково стати публічним JSON із секретними деталями.

Для читання набору id використай один запит із `ANY($1::int[])`, а не цикл із запитом на кожний id. Порожній список можна повернути одразу. Стабільне `ORDER BY` робить результат передбачуваним; якщо клієнту потрібен початковий порядок id, віднови його окремо й задокументуй політику повторів.

У практиці введи рядок, схожий на SQL injection, і переконайся, що він не повертає чужих користувачів. Потім перевір порожній список через fake db, який кидає помилку на будь-який query: так тест доводить відсутність зайвого звернення.
