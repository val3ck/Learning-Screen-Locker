## Фреймворк організує той самий HTTP

Express додає маршрутизацію й ланцюжок middleware поверх Node HTTP. Метод, шлях, заголовки та статуси залишаються основою контракту. Маршрут відповідає за конкретну операцію, а middleware може виконувати спільний крок: парсинг, request ID, автентифікацію чи логування.

```js
import express from 'express';

export function createApp() {
  const app = express();
  const products = [];
  app.use(express.json({ limit: '16kb' }));

  app.post('/products', (req, res) => {
    // Перед записом потрібна перевірка req.body.
    const product = { id: 1, name: req.body.name };
    products.push(product);
    res.status(201).location('/products/1').json(product);
  });
  return app;
}
```

Розбери порядок: спочатку `express.json` перетворює JSON-body на значення. Потім маршрут перевіряє це значення, змінює стан і формує відповідь. Сам парсинг не гарантує, що `name` існує або є рядком. Ліміт тіла контролює обсяг, а валідація — зміст.

`201 Created` повідомляє про створення ресурсу. `Location` дає його адресу, за якою клієнт може виконати GET. Для відсутнього продукту повертаємо `404`. Спробу створити продукт із неправильною ціною обробляємо як `400`, залишаючи колекцію незмінною.

## Життєвий цикл застосунку

Функція `createApp` повертає застосунок без запуску постійного порту. Entry point виконує `listen`, а тест підставляє застосунок у Supertest. Колекція оголошується всередині фабрики: два тести отримують незалежний стан.

Масив є явно навчальним сховищем одного процесу. Він втрачає дані після перезапуску і не синхронізується між кількома інстансами сервера. Цього достатньо, щоб дослідити HTTP-поведінку, після чого repository замінюється PostgreSQL без зміни зовнішнього API.

Зверни увагу на розмір відповідальності маршруту. Коротка валідація й виклик операції читаються добре. Коли всередині з’являються SQL, поштовий сервіс та складне правило ціни, виділи бізнес-операцію в окремий модуль. Тоді HTTP-шар перекладає запит у дію, а не стає єдиним місцем усіх рішень.
