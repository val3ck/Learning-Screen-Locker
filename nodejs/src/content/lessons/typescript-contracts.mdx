## Контракт — це спільна домовленість

У JavaScript помилка форми об’єкта часто проявляється далеко від місця його створення. TypeScript переносить частину перевірок у редактор і компілятор: функція описує, які значення приймає та що повертає. Це особливо корисно на межах модулів, де автор виклику не бачить реалізації.

```ts
type OrderLine = {
  readonly priceCents: number;
  readonly quantity: number;
};

function subtotal(line: OrderLine): number {
  return line.priceCents * line.quantity;
}

subtotal({ priceCents: 1250, quantity: 2 }); // 2500
// subtotal({ price: 1250, quantity: 2 }); // помилка компілятора
```

Спочатку прочитай назви полів: одиниця вимірювання входить до контракту. Значення `1250` означає копійки. Це прибирає двозначність, яку створює абстрактне поле `price`. Далі зверни увагу на `readonly`: функція не має змінювати ціну чи кількість через цей тип. Це перевірка компілятора, а не заморожування об’єкта під час виконання.

## Межа можливостей типів

Тип `number` допускає дроби, від’ємні числа, `NaN` та `Infinity`. Він не виражає правило «ціла невід’ємна ціна». Такі бізнес-обмеження перевіряє виконуваний код. Для цілих значень, які мають залишатися точними, корисний `Number.isSafeInteger`. Переповнення може виникнути і після множення двох коректних чисел, тому перевіряй також результат.

TypeScript використовує структурну типізацію: важлива форма значення. `type` зручно комбінувати з unions, `interface` — описувати розширювані контракти об’єктів. Обидва підходять для цього прикладу; послідовність у проєкті важливіша за механічний вибір одного слова.

Після компіляції опис `OrderLine` зникає. Сервер не почне автоматично перевіряти отриманий JSON. Зовнішній ввід потребує окремого валідатора — це наступний урок.

Перед практикою поясни вголос три незалежні речі: форму рядка замовлення, одиниці грошей і правила допустимих значень. Тоді напиши реалізацію, перевір порожній кошик та спробуй передати некоректний рядок навмисно.
