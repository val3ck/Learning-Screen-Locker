## Тест описує обіцянку модуля

Unit-тест перевіряє невелику одиницю поведінки без випадкової залежності від бази, мережі чи часу. Одиниця не обовʼязково є одним методом. Зручна межа — бізнес-операція з чітким входом і результатом. Спочатку сформулюй контракт словами, потім обери приклади, які відрізняють правильне рішення від правдоподібного помилкового.

```ts
import { describe, expect, test } from "@jest/globals";
describe("quote", () => {
 test.each([[0, 100], [25, 75], [100, 0]])(
  "discount %i percent", (percent, expected) => {
   expect(quote([{ price: 100, quantity: 1 }], percent).total)
    .toBe(expected);
  });
 test("rejects negative price", () => {
  expect(() => quote([{ price: -1, quantity: 1 }], 0)).toThrow();
 });
});
```

Розділення arrange, act, assert робить причину помилки видимою: підготуй вхід, виконай дію, перевір спостережуваний результат. Не привʼязуй тест до приватного методу, якщо він не є контрактом. Інакше корисний рефакторинг ламатиме тести без зміни поведінки.

Для грошей визнач одиниці й політику округлення. У вправі це цілі копійки та одне округлення знижки від subtotal. Числа з плаваючою крапкою не слід випадково змішувати з цілими копійками. Крайні значення 0% і 100% часто виявляють помилкові формули.

Асинхронний тест має повернути або await-нути promise. Інакше runner може повідомити успіх до завершення операції. Годинник, генератор ID та transport інʼєктують, коли потрібна детермінованість. Mock не доводить, що справжня база чи HTTP-клієнт працює так само: для цього буде окремий інтеграційний рівень.

Завантажувана робота використовує вбудований node:test, щоб почати без додаткового runner. Після виправлення функції перенеси ті самі поведінкові сценарії в Jest. Результат повинен залишитися однаковим: бібліотека assertion змінює синтаксис, а не сенс тесту.
