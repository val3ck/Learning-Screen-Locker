## План випускного пет-проєкту рівня Strong Junior / Mid

Синтетичні тудушки рекрутери прогортають за 3 секунди. Твій фінальний проєкт на GitHub має показувати інженерну зрілість: правильну роботу з грошима й конкурентністю, чисту архітектуру, тести, інфраструктуру та документацію.

Найсильніший сценарій для твого стеку — **Сервіс бронювання / Замовлень або Платформа вакансій**, де:
- **Публічний Backend API (`NestJS + TypeScript`)**: модульна архітектура (`Auth`, `Users`, `Bookings/Jobs`), DTO-валідація (`class-validator` або `Zod`), `@nestjs/swagger` на `/docs`.
- **PostgreSQL (`Prisma` або `pg`)**: реальні міграції, `CHECK`/`UNIQUE` інваріанти, транзакції під навантаженням (`FOR UPDATE` або умовний `UPDATE`), курсорна пагінація, відсутність N+1.
- **Безпека**: хешування паролів (`argon2`), Access JWT (`jose`) + Refresh Token у `HttpOnly` cookie, `helmet`, `CORS`, перевірка власника ресурсу (`tenantId` / `ownerId`), редагування секретів у логах (`pino`).
- **Надійність + Go бонус**: Redis cache-aside для гарячих списків + черга `BullMQ` (або інтеграція по HTTP/RabbitMQ зі своїм **Go-мікросервісом** на кшталт `JobParser` через `AbortSignal.timeout` + `Zod` контракт).
- **Тести і запуск**: unit + `Supertest` інтеграційні тести + хоча б 1 тест конкурентності через `Promise.all`, `docker compose up` (`api + postgres + redis + go-worker`) і зелений `.github/workflows/ci.yml`.

```text
POST /bookings (Idempotency-Key: uuid)
  ├─ 201 Created  → слот зарезервовано в транзакції, повернуто booking
  ├─ 200 / 201    → точний повтор з тим самим ключем повертає збережений booking (без дубля!)
  ├─ 400 Bad Req  → невалідний DTO (відсіяно до БД)
  ├─ 401 / 403    → немає JWT або спроба змінити чужий ресурс
  └─ 409 Conflict → слот уже зайнятий іншим паралельним запитом АБО idempotency key з іншим slotId
```

## 8 питань, які треба вміти пояснити на технічному захисті

1. Чому перевірка `if (await exists()) create()` без транзакції та `UNIQUE` constraint ламається під двома одночасними запитами?
2. Як працює `Idempotency-Key`, коли клієнт двічі натиснув «Оплатити/Забронювати» чи відвалився інтернет?
3. Як влаштований ваш захист від `N+1` і чому для глибоких списків ви обрали `keyset` cursor замість `OFFSET`?
4. Яка різниця між `401`, `403` та `404`, і як ви захистили маршрути від IDOR (читання чужого ID)?
5. Що станеться з кешем у Redis після оновлення запису в БД або тимчасового падіння самого Redis?
6. Якщо воркер виконав запис у БД і впав до `ack` в черзі — як ви гарантуєте відсутність дубля?
7. Як реалізовано graceful shutdown (у якому порядку закриваються HTTP, черги й пул БД при `SIGTERM`)?
8. Як ваш Node.js сервіс спілкується з Go-мікросервісом і що буде, якщо Go зависне на 30 секунд?

У фінальній лабораторній нижче ти напишеш транзакційне ядро `book(userId, slotId, key, store)` із захистом від гонки та конфлікту `Idempotency-Key` — а потім перенесеш його на реальний PostgreSQL із `UNIQUE(slot_id)` та `UNIQUE(user_id, key)`.
