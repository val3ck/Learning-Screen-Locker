## Від файла до відтворюваного запуску

Node.js виконує JavaScript поза браузером. Термінал передає команді рядки аргументів, операційна система створює процес, а Node завантажує модуль. У цьому ланцюжку корисно розрізняти поточну папку, шлях до файла та версію runtime. Якщо команда не знаходить файл, спочатку перевір папку запуску, а не переписуй програму.

~~~sh
node --version
npm --version
node app.mjs --port 4000
~~~

Файл із розширенням .mjs є ES-модулем. Для звичайних .js це визначає поле type у package.json. Імпортуй локальні модулі з явним розширенням; назва пакета означає пошук установленої залежності.

~~~js
// options.mjs
export function portFrom(args) {
  const position = args.indexOf('--port');
  return position === -1 ? 3000 : Number(args[position + 1]);
}
// app.mjs
import { portFrom } from './options.mjs';
console.log(portFrom(process.argv.slice(2)));
~~~

Перші два елементи process.argv описують виконуваний Node та файл програми. Решта належать користувачу. Усі вони спочатку рядки: напис «4000» ще треба перевірити й перетворити. Простий приклад вище пояснює потік даних, але пропущене значення чи невідомий прапорець він коректно не обробляє. Це завдання лабораторної.

## Роль npm і Git

package.json описує команди та залежності. Lockfile фіксує конкретні версії; його зберігають разом із кодом. npm ci відтворює зафіксоване дерево залежностей, коли lockfile вже існує. Власний код, тести й інструкції потрапляють у Git; node_modules та секрети виключають через .gitignore.

Перш ніж змінювати файл, сформулюй очікувану поведінку. Після зміни виконай тести й переглянь diff. Невеликий осмислений commit простіше перевірити та відкотити. Команди npm scripts створюють спільний словник: «запустити», «перевірити», «зібрати» мають однаково працювати після нового клонування.

Практику почни з читання тестів. Вони є виконуваними прикладами контракту. Навмисно незавершений starter має падати; після реалізації команда повинна завершитися нульовим кодом.
