## Транзакція зберігає спільний інваріант

Переказ має дві зміни: списання й зарахування. Якщо друга впаде, перша не повинна залишитися окремо. Транзакція робить ці зміни спільним блоком: або COMMIT, або ROLLBACK. Для PostgreSQL цей блок належить конкретному з’єднанню.

```js
const client = await pool.connect();
try {
  await client.query('BEGIN');
  const debit = await client.query(
    'UPDATE accounts SET balance=balance-$1 WHERE id=$2 AND balance >= $1 RETURNING id',
    [amount, fromId]
  );
  if (debit.rows.length === 0) throw new Error('Недостатньо коштів');
  const credit = await client.query(
    'UPDATE accounts SET balance=balance+$1 WHERE id=$2 RETURNING id', [amount, toId]
  );
  if (credit.rows.length === 0) throw new Error('Одержувач відсутній');
  await client.query('COMMIT');
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

Усі запити використовують один client. Окремі `pool.query` можуть потрапити на різні з’єднання, тому не утворюють потрібної транзакції. У виробничому коді також продумай відмову самого rollback, щоб не втратити початкову причину.

Умовний UPDATE перевіряє достатній баланс разом зі списанням. Це надійніше за окремі SELECT і UPDATE, між якими може втрутитися інша транзакція. Відсутній одержувач кидає помилку та повертає списані кошти через rollback.

Простеж два запити, які одночасно списують із рахунку 500 по 400. Перший `UPDATE` змінить баланс на 100. Другий чекатиме потрібне блокування рядка, після чого PostgreSQL знову перевірить умову `balance >= 400` для актуальної версії рядка. Він не отримає рядка з `RETURNING`, і твій код відхилить переказ. Саме так умова в операторі запису захищає інваріант; перевірка балансу в JavaScript перед `UPDATE` цього не гарантує.

## Ізоляція не означає відсутність конкурентності

За Read Committed кожний statement бачить власний snapshot. Repeatable Read тримає стабільніший погляд усередині транзакції, а Serializable може відхилити конфліктне виконання. Після serialization failure повторюють усю транзакцію з обмеженням спроб. Взаємне захоплення блокувань може спричинити deadlock навіть для коректних окремих операцій.

Повторюй лише відомі тимчасові відмови, наприклад SQLSTATE `40001` або `40P01`, і запускай заново весь блок від `BEGIN`. Лист, webhook чи інший зовнішній ефект усередині повторюваного блоку може відбутися двічі; для нього потрібен окремий механізм доставки. Якщо з’єднання зникло під час `COMMIT`, клієнт може не знати, чи запис зафіксовано. У такому разі сліпий повтор без ключа ідемпотентності небезпечний.

Автотест цієї вправи використовує fake client і перевіряє керування BEGIN/COMMIT/ROLLBACK та release. Він не доводить поведінку справжніх блокувань. Додаткове завдання запускає Docker PostgreSQL і два clients, щоб відтворити конкурентні списання. Саме там перевіряємо інваріант під навантаженням.

Перевірку суми виконуй до отримання з’єднання. Вона не потребує бази, тому неправильний запит не має витрачати ресурс pool. Обмеження самої таблиці додатково забороняє від’ємний баланс.
