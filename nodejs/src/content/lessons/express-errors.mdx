## Клієнт і оператор потребують різних деталей

Користувачу потрібне зрозуміле повідомлення та стабільний код помилки. Оператору потрібні контекст і стек для пошуку причини. Якщо повернути весь об’єкт помилки клієнту, разом із ним можуть витекти SQL, шлях до файлу або секрет з повідомлення драйвера.

Очікувану відмову, наприклад відсутність користувача, можна описати доменною помилкою з дозволеним публічним кодом. Неочікувана відмова отримує узагальнений `500`, а деталі залишаються у внутрішній діагностиці.

```js
app.get('/users/:id', async (req, res) => {
  const user = await service.findUser(req.params.id);
  if (!user) throw new DomainError(404, 'USER_MISSING', 'Користувача немає');
  res.json(user);
});

app.use((error, req, res, next) => {
  if (res.headersSent) return next(error);
  const known = error instanceof DomainError;
  res.status(known ? error.status : 500).json({
    error: {
      code: known ? error.code : 'INTERNAL_ERROR',
      message: known ? error.message : 'Внутрішня помилка сервера'
    },
    requestId: req.requestId
  });
});
```

У цьому курсі використовується Express 5: rejected Promise, повернутий async-handler, передається в error middleware автоматично. Для callback-коду або від’єднаних фонових Promise це правило не дає автоматичного захисту. Такі операції потребують явного життєвого циклу й обробки відмови.

## Кореляція без секретів

На початку запиту створюємо request ID і повертаємо його в заголовку та помилці. З тим самим ID пишемо внутрішній лог. Клієнт може повідомити цей ідентифікатор, а оператор знайде потрібну подію без пересилання приватного тіла запиту.

Error middleware має чотири параметри та розташовується після звичайних маршрутів. Окремі middleware перетворюють неправильний JSON і відсутній маршрут на узгоджені помилки. Коли заголовки вже відправлені, повторна JSON-відповідь неможлива; передаємо керування далі.

У тесті навмисно створи помилку з рядком `password=secret`. Переконайся, що рядок не потрапляє у відповідь. Це невелика, але змістовна перевірка публічної межі сервісу.

Код помилки зберігай стабільним між релізами: клієнт може реагувати на нього програмно. Людинозрозумілий текст можна локалізувати, не змінюючи спосіб обробки помилки.
