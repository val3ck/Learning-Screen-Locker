## Що отримує HTTP-сервер

Клієнт спершу знаходить адресу через DNS, встановлює з’єднання, а для HTTPS узгоджує TLS. У типовому розгортанні TLS може завершувати reverse proxy; Node отримує HTTP-запит усередині інфраструктури. Це не звільняє застосунок від перевірки користувача, ресурсів і даних.

HTTP-запит має метод, цільовий URL, заголовки та необов’язкове тіло. Шлях і query виконують різні ролі: `/items` називає колекцію, а `?limit=2` уточнює спосіб читання. Query є зовнішнім текстом, навіть коли в ньому написано число.

```js
import { createServer } from 'node:http';

const server = createServer((req, res) => {
  const url = new URL(req.url ?? '/', 'http://localhost');
  if (req.method === 'GET' && url.pathname === '/health') {
    res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });
    return res.end(JSON.stringify({ ok: true }));
  }
  res.writeHead(404, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ error: 'NOT_FOUND' }));
});
```

Спочатку сервер розбирає URL. Потім вибирає гілку за методом і шляхом. Перед тілом встановлює статус та тип вмісту. `return` у завершеній гілці не дозволяє випадково перейти до другої відповіді. У тесті сервер запускається на тимчасовому порту й закривається у `finally`.

## Статуси є частиною контракту

`400` означає неправильний запит, `404` — невідомий ресурс, `405` — недозволений метод для відомого ресурсу. Для `405` корисний заголовок `Allow`, який перелічує доступні методи. Внутрішня помилка має іншу природу й не повинна маскуватися під клієнтський `400`.

Cookie — спосіб передавання стану через заголовки, а не автоматична система авторизації. CORS керує тим, чи дозволить браузерному JavaScript прочитати cross-origin-відповідь. Він не блокує всі сторонні HTTP-клієнти й не замінює серверних прав доступу.

Власноручний сервер робить ці кроки видимими. У наступних модулях фреймворк скоротить повторюваний код, але відповідальність за коректність HTTP-контракту залишиться у твоєї програми.
